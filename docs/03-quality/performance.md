# Отчет о производительности (ЛР3)

## 1. Цель производительности
- **Ключевой сценарий:** Загрузка каталога экскурсий (главная страница).
- **Целевые показатели:** p95 времени ответа ≤ 300 мс при 50 RPS, доля ошибок < 1%.

## 2. Тестовые данные и инструменты
- **Данные:** 10 000 записей в таблице `excursions` (сгенерированы через `LoadTestSeeder`).
- **Инструмент:** k6 (сценарий `load/load_test.js`).
- **Нагрузка:** 50 виртуальных пользователей, длительность 2 минуты.

## 3. Базовая линия (до оптимизации)
- **RPS:** 33.5
- **p(95):** 235.68 ms
- **Ошибки:** 0.00%

## 4. Найденное узкое место
- Проблема **N+1** в компоненте `ExcursionsList` (задача TD-3).
- При росте базы до 10 000 записей время ответа выросло до 314 ms из-за отсутствия индекса на поле `status`.

## 5. Примененные оптимизации
1. **Оптимизация №1 (неудачная):** Добавление тяжелых связей (`schedules`, `pricingRules`) в `with()`. Привело к деградации (p95 = 314 ms). Откатили.
2. **Оптимизация №2 (успешная):** Добавление **индекса** на поле `status` в таблице `excursions`. Ускорило фильтрацию одобренных экскурсий.

## 6. Таблица «До / После»

| Метрика | До оптимизации | После оптимизации | Изменение |
| :--- | :--- | :--- | :--- |
| **RPS** | 33.5 | 33.2 | -0.9% |
| **p(95)** | 314.00 ms | 276.85 ms | **-11.8%** |
| **Доля ошибок** | 0.00% | 0.00% | 0% |

*(Примечание: RPS незначительно снизился из-за стабильности нагрузки, но главное — время ответа p95 упало ниже целевого порога).*

## 7. Оценка по закону Амдала
- Формула: `S = 1 / (1 - P + P/S)`
- Время ответа снизилось с 314 ms до 276 ms. Ускорение критического пути составило примерно **12%**. Это подтверждает, что добавление индекса на `status` было правильным и эффективным решением.

## Вывод
Целевой показатель p95 ≤ 300 ms достигнут (276.85 ms). Узкое место устранено.
