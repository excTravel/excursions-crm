# Стратегия ветвления и правила слияния

## Цель
Зафиксировать процесс работы с Git, чтобы обеспечить стабильность основной ветки и прозрачность ревью.

## Исходные данные
Команда из 2 человек. Проект на Laravel, используется GitHub.

## Ход

### Выбранная стратегия: GitHub Flow
Мы выбрали **GitHub Flow**, так как команда маленькая, а процесс должен быть простым и гибким.
- Ветка `main` всегда готова к деплою.
- Любое изменение происходит в отдельной ветке.
- Изменения попадают в `main` только через Pull Request.

### Именование веток
- Новые фичи: `feature/us-<номер>` (например, `feature/us-1`).
- Документация и инфраструктура: `docs/<тема>`, `ci/<тема>`.
- Исправление ошибок: `bugfix/<краткое-описание>`.

### Правила слияния (Merge Rules)
1. Прямые коммиты в `main` **запрещены** (настроена защита ветки).
2. Любое изменение попадает в `main` только через Pull Request.
3. Pull Request должен быть одобрен (Approve) вторым участником команды.
4. Pull Request не может быть смержен, если CI завершился с ошибкой.
5. Используется **Squash and Merge** для чистой истории.

### Соглашение о сообщениях коммитов (Conventional Commits)
Формат: `<тип>: <описание>`.
- `feat: ...` — новая функциональность.
- `fix: ...` — исправление бага.
- `docs: ...` — документация.
- `ci: ...` — настройка конвейера.
- `chore: ...` — рутинные задачи.

## Выводы
Стратегия GitHub Flow с защитой `main` и обязательным ревью позволяет избежать случайных поломок.

## Итог
Правила зафиксированы. Защита ветки настроена.
