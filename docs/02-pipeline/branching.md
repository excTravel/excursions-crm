# Стратегия ветвления и правила слияния

## Цель
Зафиксировать процесс работы с Git, чтобы обеспечить стабильность основной ветки и прозрачность ревью.

## Исходные данные
Команда из 2 человек. Проект на Laravel, используется GitHub.

## Ход

### Выбранная стратегия: GitHub Flow
Мы выбрали **GitHub Flow**, так как:
- Команда маленькая (2 человека).
- Нет необходимости поддерживать несколько версий в продакшене одновременно.
- Процесс простой: любое изменение (фича, багфикс, документация) происходит в отдельной ветке, которая затем сливается в `main` через Pull Request.
- Ветка `main` всегда готова к деплою.

### Именование веток
- Новые фичи: `feature/us-<номер>` (например, `feature/us-1`).
- Документация: `docs/<тема>` (например, `docs/lab2-pipeline`).
- Исправление ошибок: `bugfix/<краткое-описание>`.

### Время жизни ветки
Ветка живет от момента создания до успешного слияния в `main`. После слияния ветка удаляется (как локально, так и на GitHub), чтобы не засорять репозиторий.

### Правила слияния (Merge Rules)
1. Прямые коммиты в `main` **запрещены** (включена защита ветки).
2. Любое изменение попадает в `main` только через Pull Request.
3. Pull Request должен быть одобрен (Approve) вторым участником команды.
4. Pull Request не может быть смержен, если CI (Continuous Integration) завершился с ошибкой.
5. Слияние происходит через **Squash and Merge** (чтобы история коммитов в `main` была чистой).

### Соглашение о сообщениях коммитов (Conventional Commits)
Мы используем стандарт Conventional Commits. Формат: `<тип>: <описание>`.
- `feat: ...` — новая функциональность.
- `fix: ...` — исправление бага.
- `docs: ...` — изменения в документации.
- `chore: ...` — рутинные задачи (настройка CI, обновление зависимостей).
Пример: `feat: add user registration endpoint`.

## Выводы
Стратегия GitHub Flow с защитой `main` и обязательным ревью позволяет избежать случайных поломок и поддерживать чистую историю коммитов.

## Итог
Правила зафиксированы. Защита ветки настроена.
