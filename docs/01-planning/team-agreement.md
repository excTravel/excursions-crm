## 2. Каналы коммуникации

Для поддержания связи используются следующие инструменты:
- Telegram: Основной канал для оперативной связи, согласования встреч и уведомлений о готовности задач.
- GitHub Issues и Pull Requests: Рабочая среда для обсуждения технических деталей, фиксации замечаний по коду и документации, а также для проведения формального ревью.
- Асинхронная коммуникация: Вопросы, не требующие немедленного ответа, оставляются в комментариях к PR или в виде текстовых сообщений.

## 3. Регламент синхронизации

- Ежедневный статус (асинхронно): Участники направляют краткий отчет о проделанной работе и текущих блокерах в Telegram до 21:00.
- Синхронные созвоны: Проводятся по мере необходимости, но не реже двух раз в неделю. Основные цели — проведение Planning Poker, совместное разрешение сложных технических вопросов и планирование этапов работы.
- Соблюдение дедлайнов: Все изменения, относящиеся к текущему этапу проекта, должны быть зафиксированы в репозитории не позднее чем за 24 часа до установленного срока сдачи.

## 4. Правила ревью (Code Review)

1. Изоляция изменений: Любые модификации основной ветки (`main`) осуществляются исключительно через создание Pull Request (PR).
2. Обязательное ревью: Автор PR не имеет права выполнять слияние (merge) без предварительного одобрения (Approve) от второго участника команды.
3. Критерии проверки: Ревьюер обязан проверить отсутствие конфликтов, соответствие изменений критериям приёмки, работоспособность скриптов и корректность оформления Markdown-документов.
4. Сроки проведения: Ревью выполняется в течение 24 часов с момента создания PR. В случае задержки автор уведомляет ревьюера в Telegram.
5. Исключительные случаи: При критической блокировке процесса автор вправе выполнить слияние без ревью, однако обязан немедленно уведомить второго участника и обосновать свое решение в комментариях к PR.

## 5. Порядок разрешения разногласий

1. Аргументация: Стороны обосновывают свою позицию фактами, расчетами (результатами скриптов) или ссылками на нормативные материалы и лекции.
2. Поиск компромисса: При возникновении разногласий в ходе Planning Poker приоритет отдается оценке, имеющей четкое обоснование рисков. При отсутствии подтвержденных рисков принимается меньшая оценка.
3. Эскалация: Если консенсус не достигнут, решение принимается путем переговоров. В случае тупиковой ситуации допускается обращение за консультацией к преподавателю.
4. Документирование: Все принятые в спорных ситуациях решения фиксируются в соответствующих документах в папке docs/01-planning/ с кратким обоснованием.

## 6. Критерии готовности (Definition of Done)

Задача или этап считаются завершенными при соблюдении следующих условий:
- Изменения закоммичены и отправлены в удаленный репозиторий.
- Pull Request получил статус Approve от второго участника.
- Документация в docs/01-planning/ актуальна и не содержит незаполненных заглушек.
- Скрипты (`release_planner.py`, monte_carlo.py, `pert_cpm.py`) успешно запускаются на актуальных данных без ошибок.
- Задача перемещена в колонку Done на Kanban-доске.
