# Процесс и доска

## Цель
Обосновать WIP-лимиты, определить DoR/DoD и зафиксировать методологию.

## Исходные данные
Доска: Бэклог → Ready → In Progress → Review → Done. Команда 2 человека. 4 недели до защиты.

## Ход

### WIP-лимиты по закону Литтла
Формула: `WIP = Пропускная способность × Время цикла`.

- Пропускная способность (throughput): 2 истории в неделю (на основе ёмкости 13 SP и среднего размера истории ~5 SP).
- Время цикла (cycle time): 3 дня (0.6 недели).
- WIP = 2 × 0.6 = 1.2 → **лимит 2 на «In Progress»**.

Для «Review»: пропускная способность та же, время цикла 1 день (0.2 недели) → WIP = 0.4 → **лимит 1 на «Review»**.

«Бэклог» и «Done» — без лимита: бэклог содержит все истории, Done накапливает завершённые.

### DoR (Definition of Ready)
История готова к работе, если:
- есть текст в формате «Как…, я хочу…, чтобы…»;
- есть минимум 2 критерия Дано/Когда/Тогда;
- размер проставлен по шкале Фибоначчи;
- зависимости определены;
- история входит в текущий MVP или приоритизирована по WSJF.

### DoD (Definition of Done)
История считается завершённой, если:
- код реализован и проходит ревью;
- критерии приёмки проверены;
- документация обновлена (если применимо);
- история перемещена в «Done» на доске.

### Методология
Выбран **Kanban**, потому что:
- команда маленькая (2 человека);
- работа идёт потоком, без фиксированных спринтов;
- WIP-лимиты и закон Литтла применимы напрямую;
- защита требует обоснования лимитов — в Kanban это нативно.

## Выводы
WIP-лимиты: In Progress = 2, Review = 1. Бэклог и Done без лимита. DoR/DoD согласованы. Методология — Kanban.

## Итог
Доска настроена, лимиты обоснованы, процесс описан.
